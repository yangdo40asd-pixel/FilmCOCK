## 1. 목표와 범위

동작 중인 기능을 유지하면서 프로젝트를 처음 보는 사람이 문제 정의, 코드 책임, 데이터 흐름, 검증 근거와 개발 기여를 이해할 수 있도록 정리한다.

컴퓨터공학과 전체에 공통으로 강제되는 폴더 구조가 있다는 전제는 사용하지 않는다. 현재 학교·수업·캡스톤의 제출 규정은 제공되지 않았다. 아래 구조는 소프트웨어공학 산출물과 개발 포트폴리오를 설명하기 위한 제안이며, 별도의 제출 규정이 있으면 문서 이름과 제출 형식을 맞춘다.

최초 계획 단계에서는 읽기 전용 조사와 이 문서만 작성했다. 이후 사용자의 순차 작업 요청으로 구현을 시작했다. 실제 이동·코드 변경·보존 내역은 [작업 기록](REFACTORING_LOG.md)을 따른다. 앱 실행, 빌드, 정적 분석, 자동 테스트, API 호출은 실행하지 않았다. GitHub 커밋·푸시는 아직 진행하지 않았다.

### 반드시 유지할 사용자 요구

- 시작 화면에서 홈 데이터를 미리 받아 홈 진입 시 큰 로딩 표시를 줄인다.
- 홈 추천 제목은 `오늘의 추천 영화 (ISTJ)`처럼 MBTI만 표시한다. 장르명을 제목에 다시 붙이지 않는다.
- 홈·취향·챗봇에서 동일한 MBTI·선호 장르 저장값을 사용한다.
- 좋아요·봤어요·댓글·인물 좋아요 변경이 마이페이지에 반영된다.
- 로그인 유지, 계정 구분, 비회원 시작 정책을 구조 정리 과정에서 임의로 바꾸지 않는다.
- 챗봇 질문 칩은 규칙 기반, 자유 입력은 설정에 따라 LLM을 사용하며 실패 시 규칙 기반으로 대체한다.
- 코드·설정·문서는 Codex가 수정하고, 실기기·에뮬레이터 실행과 빌드는 사용자가 담당한다.
- 이전에 허용한 자체 정적검사 1회는 이미 사용됐다. 이 계획이 새 실행 권한을 의미하지 않는다.
- 사용자 실테스트는 기존 2개 묶음을 유지한다. 기능별 확인 사항은 그 안에 추가한다.

## 2. 조사 범위와 확인 수준

조사 시작 시 작업 트리는 깨끗했다. 파일 목록, 주요 의존성, 시작 흐름, 저장소, API 계층, 홈 데이터 준비, 추천 서비스, 챗봇·LLM 연결, 테스트 소스와 기존 문서를 확인했다. 모든 화면의 실제 동작을 재검증한 것은 아니다.

| 영역 | 현재 확인한 내용 | 리팩토링 시 의미 |
| --- | --- | --- |
| 앱 코드 | `lib/`에 Git 추적 Dart 파일 80개 | 단일 Flutter 패키지를 유지하며 단계적으로 정리 가능 |
| 테스트 | `test/`에 8개 파일 | 이름·위치·가짜 의존성을 정리하되 실행 결과를 새로 주장하지 않음 |
| 문서 | 루트 README·보수 체크리스트, `docs/`의 MD 1개와 TXT 3개 | 최신 사용 설명과 과거 설계·작업 기록이 섞임 |
| UI 상태 | `setState`, `FutureBuilder`, 컨트롤러, 변경 알림이 혼용 | 라이브러리 교체보다 상태 소유자·수명·갱신 규약 정리가 먼저 |

## 3. 코드와 문서에서 발견한 정리 과제

### 3.1 구조·코드

1. 계층별 폴더는 있으나 한 기능을 이해하려면 `models`, `services`, `repositories`, `screens`를 반복해서 오가야 한다.
2. 화면에서 `FirebaseAuth`, `SharedPreferences`, `ApiService`에 직접 접근하는 부분이 남아 있다. 화면 분리와 별개로 데이터 접근 책임을 이동해야 한다.
3. `HomeController`는 Future 묶음을 보관하고 `SearchScreenController`는 ChangeNotifier를 사용한다. 공통 상태 규칙 없이 모든 화면을 한 상태관리 패키지로 교체하면 변경 범위가 커진다.
4. `movie_model.dart`에 영화 외 관련 타입이 함께 있다. 실제 참조를 기준으로 영화·인물·장르·영상·시청 제공자 모델을 나눌 후보이다.
5. 활동 저장은 목록과 개별 불리언을 별도로 저장하며 화면이 두 값을 조정한다. 저장소 내부의 단일 변경 작업, 연속 입력 순서, 실패 복구를 함께 설계해야 한다.
6. MBTI·장르는 소유자별 키를 쓰지만 활동 목록·프로필·달력은 같은 수준으로 분리돼 있지 않다. 로그아웃 정리는 모든 사용자 범위 키를 지운다. 계정 전환 시 보존·삭제 정책을 명확히 하고 이관 전에 문서화해야 한다.
7. 여러 SharedPreferences 쓰기 작업은 원자적 트랜잭션이 아니다. 예외뿐 아니라 쓰기 결과도 확인하고, 완료 상태를 마지막에 확정하는 저장 규약이 필요하다.
8. 추천에서 장르 집합을 `take(3)`로 제한한다. 선택 장르가 많으면 MBTI 장르가 뒤에서 제외될 수 있다. 현재 정책을 먼저 명세하고, 가중치·우선순위 변경은 구조 변경과 분리한다.
9. `MbtiDetailScreen`의 `_genreIdMap`이 공통 `GenreCatalog`와 별도로 존재한다. 매핑의 단일 출처가 필요하다.
10. `mbti_screen.dart`는 선언 외 호출이 검색되지 않았다. 진입 경로·테스트·외부 참조를 다시 확인한 뒤 제거 또는 이전 화면으로 기록한다.
11. 정적 서비스와 전역 캐시가 많다. 테스트용 저장소·네트워크·시계 주입을 필요한 지점부터 적용한다. 기존 `LlmClient`와 영화 검색 주입은 유지·확장할 수 있는 출발점이다.
12. 중첩 gitlink는 일반 파일 이동 대상이 아니다. 내부 `.git`의 커밋·원격·미커밋 파일부터 확인하고 복구 가능한 보관 위치를 확보해야 한다.

위 항목은 정리 및 위험 검토 대상이다. 이번 조사만으로 모든 항목을 사용자에게 재현되는 장애로 판정하지 않는다.

### 3.2 문서·재현성

- README의 홈 캐시 설명은 메모리만 언급하지만 코드에는 `HomeCacheStorage` 디스크 저장·복구가 있다.
- `FirebaseLlmClient` 주석의 App Check 보호 설명과 현재 의존성·README의 미사용 설명이 다르다. 실제 설정 확인 후 일치시켜야 한다.
- 과거 설계 TXT에는 향후 계획과 현재 구현이 혼재한다. 그대로 최신 설계서로 승격하지 않는다.
- 보수 체크리스트의 과거 통과 기록은 현재 커밋 검증 결과가 아니다. 날짜·커밋·검증 담당자를 분리해 남긴다.
- `test/widget_test.dart`는 실제로 모델 파싱 테스트다. 파일명과 책임을 일치시킨다.
- 일부 챗봇 테스트는 실제 서비스 기본값을 사용한다. 실제 API 접근 여부를 차단할 수 있도록 모든 외부 조회를 가짜 구현으로 대체하는 작업이 필요하다.
- 챗봇 테스트 초기값의 `user_mbti`와 현재 소유자별 키 방식이 다르다. 저장소를 통한 준비 또는 공통 fixture로 맞춘다.
- `pubspec.yaml`의 설명은 기본 템플릿이며 CI 설정과 포트폴리오용 기여·설계 결정·회고 문서가 없다.
- 생성 인물 데이터에는 생성 표시가 있지만 현재 `tool/` 목록만으로 생성 과정을 재현할 수 없다. 원본·도구가 없으면 이를 명시하고 재생성 가능하다고 주장하지 않는다.

## 4. 목표 폴더 구조

기능별 구조를 적용하되, 모든 기능에 빈 `domain/data/application` 폴더를 기계적으로 만들지 않는다. 정책·저장·화면이 실제로 존재하는 경우에만 해당 폴더를 둔다. `src/`나 `backend/`를 형식상 추가하거나 Flutter 플랫폼 폴더를 다른 곳으로 옮기지 않는다.

### 코드 배치 규칙

- 기능 내부는 `presentation/`(표시), `application/`(흐름·상태), `domain/`(정책·계약), `data/`(저장·외부 연동)로 필요한 만큼 나눈다.
- 화면은 컨트롤러·애플리케이션 서비스를 호출하고, 애플리케이션은 저장소 계약에 의존한다. Firebase·HTTP·SharedPreferences 구현은 조립 지점에서 주입한다.
- `domain/`은 Flutter UI, Firebase SDK, SharedPreferences를 import하지 않는다.
- `shared/`는 실제 공용 타입·외부 조회 계약·위젯만 가진다. 기능 하나에서만 쓰는 코드를 편의상 몰아넣지 않는다.
- 홈·챗봇·취향은 추천 기능의 공개 application/domain 계약을 사용한다. 활동·프로필도 같은 규칙을 따른다. 기능 사이 presentation 또는 data 내부 직접 참조와 순환 의존은 금지한다.
- `core/`는 범용 기반 기능이다. MBTI 추천이나 영화 등급 규칙은 core에 넣지 않는다.
- 기존 `ApiService`는 이행 중 호환 진입점으로 유지한 뒤 호출처가 모두 대체되면 제거한다.
- 상태관리 패키지 추가, DB 교체, API 공급자 변경, LLM 모델 변경은 이번 구조 변경에 묶지 않는다.

## 8. 변경 단위와 복구 원칙

1. 문서 이동, 코드 경로 이동, 동작 변경을 서로 다른 커밋으로 나눈다.
2. 파일 이동 커밋에는 해당 import·asset·문서 링크 수정만 함께 넣는다.
3. 경로를 옮길 때 문자열 참조, 테스트 import, 도구의 파일 경로, Firebase 설정도 확인한다.
4. 저장 키 이름은 폴더명을 바꿨다는 이유로 변경하지 않는다. 마이그레이션을 도입한 뒤에만 바꾼다.
5. 오래된 앱도 읽을 수 없는 새 저장 포맷을 사용했다면 코드만 이전 커밋으로 되돌려서는 안 된다. 백업과 호환·복원 정책을 적용한다.
6. 앱 에셋에 포함된 키는 빌드 결과에서 추출될 수 있다. Git 제외와 실행 파일의 비밀 보호를 같은 것으로 설명하지 않는다.
7. `.dart_tool/`, `build/`는 소스 구조 정리 대상이 아니며 생성물 제외 규칙을 유지한다.
8. 사용하지 않는 플랫폼 폴더는 삭제하지 않고 지원·미검증 범위를 문서로 표시한다. 학교 규정이나 실제 배포 범위 확정 후 별도로 판단한다.
9. 라이선스는 프로젝트 소유권·외부 자산 조건 확인 후 선택한다. 임의의 공개 라이선스를 선언하지 않는다.

## 9. 포트폴리오에서 설명할 기술 주제

| 주제 | 제시할 근거 | 과장하지 않을 내용 |
| --- | --- | --- |
| 비동기·동시성 | 검색 디바운스, 최신 응답 보호, 홈 병렬 준비 | 단일 API 제한을 앱 전체 시작 시간 상한으로 표현하지 않음 |
| 자료구조·알고리즘 | 장르 집합, 영화 ID 중복 제거, 날짜별 기록, 캐시 만료 | MBTI 규칙을 학습 모델·협업 필터링으로 표현하지 않음 |
| 소프트웨어 설계 | 기능 경계, 저장소 계약, 의존성 주입, 상태 수명 | 파일 분할만으로 아키텍처 완성을 주장하지 않음 |
| 데이터 일관성 | 계정 소유자, 저장 실패, 중복 상태, 이관 버전 | SharedPreferences를 트랜잭션 DB라고 설명하지 않음 |
| AI 연동 | LLM JSON 계획, 입력·출력 검증, TMDB 후보 확인, 규칙 대체 | 직접 학습한 모델·환각 완전 제거로 표현하지 않음 |
| 품질·운영 | 가짜 구현 테스트, 실제 결과 기록, 키 제외, 오류 복구 | 실행하지 않은 검사·개선 수치를 통과·성과로 표시하지 않음 |

프로젝트 소개에는 실제 개발 기간·팀 구성·본인 담당 범위를 근거에 맞게 채운다. 확인되지 않은 정보는 `확인 필요`로 둔다.

## 10. 다음 착수 지점

현재 수행 가능한 P0~P4 코드·문서 작업을 반영했다. 남은 미체크 항목은 사용자 실행 검증, 최신 시연 화면, 개인 기여 사실, 외부 자산의 권리 근거다. 새 장애가 확인되면 해당 재현 조건을 바탕으로 후속 코드 수정을 진행한다. 출시 실행 검증은 아직 하지 않았다. 업로드 상태와 기준 커밋은 Git 이력에서 확인한다. 세부 이력은 [작업 기록](REFACTORING_LOG.md), 경로는 [이관표](SOURCE_MIGRATION.md)를 따른다.

이 문서는 리팩토링 계획이며 현재 앱의 새 장애 수정 완료 보고서나 검증 통과 보고서가 아니다.
